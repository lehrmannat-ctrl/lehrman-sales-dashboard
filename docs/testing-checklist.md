# Testing Checklist

## What has ALREADY been executed and verified (not just written)

This sandbox had no network access to npm or a live Supabase project (see
`docs/known-limitations.md`), so testing took the form of running the
actual logic directly wherever that was possible, rather than only
reading the code back:

- [x] **All 7 SQL migrations** (`supabase/migrations/0001`–`0007`) applied
      cleanly, in order, to a real local PostgreSQL 16 instance (with a
      minimal stub of Supabase's `auth` schema — see
      `scripts/local_test_auth_stub.sql`, which must NEVER be run against a
      real Supabase project).
- [x] **`supabase/seed.sql`** (generated by `scripts/generate_seed.py`)
      loads with zero constraint violations, including the Sunday-exclusion
      `CHECK` constraints on `appointments` and `follow_up_tasks`.
- [x] **Every reporting view** (`v_funnel_summary`, `v_revenue_sold_daily`,
      `v_cash_collected_daily`, `v_avg_time_in_stage`, etc.) queried
      against the seed data and manually cross-checked (e.g. total revenue
      sold across all daily rows matches the sum of `sold`-stage
      opportunity values).
- [x] **`generate_alerts()`** executed against seed data; produced the
      expected alert types with no errors, and its idempotency (no
      duplicate open alerts on re-run) was confirmed.
- [x] **`src/lib/followup-engine.ts`** executed directly with Node's
      TypeScript stripping (`node --experimental-strip-types`) — confirmed
      18 initial-contact tasks generate correctly, confirmed a Sunday never
      appears in any generated timestamp (including cases where a shift
      pushes two days' tasks onto the same Monday), and confirmed custom
      recall-day overrides work.
- [x] **`src/lib/date-ranges.ts`** executed the same way — confirmed
      Today/Yesterday/This Week/Last Week/This Month/Last Month all
      resolve correctly against the environment's real "today," and caught
      (then fixed) an off-by-one bug in the previous-period length
      calculation for single-day ranges.
- [x] **`src/lib/kpi.ts`**'s status/percent-change/weighted-score/forecast
      functions executed with representative numbers and manually checked
      against hand calculations.
- [x] **The Stripe webhook's HMAC signature verification** executed
      against a self-generated valid signature, a tampered payload, a wrong
      secret, and a missing header — all four cases behaved correctly.
- [x] **Every `.ts`/`.tsx` file type-checked** with the globally-available
      TypeScript compiler (no project `node_modules`, so `next`, `react`,
      and `@supabase/*` all report as missing modules — expected noise,
      filtered out). After filtering missing-module errors and the ~247
      JSX-typing errors caused by `@types/react` not being installed in
      this check environment, exactly one substantive-looking error
      surfaced (`src/app/(dashboard)/dashboard/page.tsx`, a `key`/`href`
      prop mismatch on `<KpiCard>`) and it traces to the same missing-
      React-types cause, not a real type error — `KPI_DRILLDOWN_HREF` is
      explicitly typed `Record<string, string>`, so indexing it always
      returns `string`, which is assignable to `KpiCard`'s optional
      `href?: string`. **Still, run `npm run typecheck` for real once
      `npm install` has completed** — that is the authoritative check,
      this was the best available substitute without network access.

## What has NOT been executed and must be verified before going live

- [ ] `npm install && npm run build && npm run dev` — never run in this
      sandbox (no npm registry access). Do this first, before anything
      else, and fix whatever the TypeScript compiler flags.
- [ ] Every page rendered in an actual browser, light and dark, desktop
      and mobile widths.
- [ ] Supabase Auth actually configured (email/password or magic link) —
      the schema assumes `profiles.id` matches `auth.users.id`; decide
      whether a trigger auto-creates the profile row on signup or whether
      the owner creates each login manually.
- [ ] Every RLS policy tested by actually logging in as an owner and as a
      sales_associate and confirming what each can and cannot see/edit —
      the policies were only validated as *valid SQL*, not exercised
      through real authenticated sessions (no live Supabase Auth was
      available here).
- [ ] Each integration adapter tested against its real, live account per
      `docs/integration-setup-guide.md` — none of the five should be
      trusted as "connected" until this happens, Stripe included.
- [ ] The Stripe/GoHighLevel webhook routes tested with real webhook
      deliveries (use each provider's webhook-testing tool / CLI).
- [ ] `/api/cron/sync` wired to an actual scheduler and confirmed to run
      unattended.
- [ ] Mobile Safari / mobile Chrome manual pass — a solo owner will likely
      use this from a phone in the field.
- [ ] Load the app with an EMPTY database (no seed data) and confirm every
      page shows honest empty states ("No data") rather than erroring.
- [ ] Disconnect an integration (or use one with a stale/wrong key) and
      confirm the integrations page shows "error"/"not_connected" instead
      of silently showing stale data.
